ROOT CAUSES AND WHAT WAS CHANGED

1. Meta descriptions
The original source homepage description was verbose and reused by the old
single-document routing approach. The existing generator already produced
unique descriptions, but its fallback applied slice(0,165) to assembled prose.
The live audit found 24 descriptions without sentence-ending punctuation;
examples visibly stop mid-word. Many collection descriptions also described
both furniture and lighting irrespective of the collection's actual subject.
Replaced the fallback with 46 reviewed descriptions in
scripts/seo-descriptions.json. Each describes existing visible content and ends
as a complete sentence. Current lengths are 144-160 characters. Updated the
source homepage description too. Open Graph, Twitter and page schema receive
the same description automatically. Build checks reject absent or incomplete
descriptions outside Bing's stated 25-160 character range. Character length is
an editorial guardrail, not a ranking rule;
search engines can choose their own snippet text.

2. Images and the reported 47 missing alt attributes
The supplied source contains 609 image elements, zero missing alt attributes,
and originally 47 empty alternatives: 46 repeated footer brand marks plus one
decorative collection-hover preview. That matches the reported count but an
export of Bing's flagged URLs/elements is required to prove its classification.
Added alt="RJDLx" to the 46 meaningful footer marks in index.html. Kept alt=""
on the decorative hover preview because the adjacent links already convey its
purpose. Existing descriptive product/material alternatives were preserved.
No image files were renamed or replaced by invented imagery. The generated
pages expose real image sources without requiring JavaScript. Build/tests now
check image alternatives. Responsive srcset and gallery image file references
were also checked locally; no missing files were found.

3. Multiple H1 tags
The authoring index.html intentionally contains all 46 views, each with its own
H1. Publishing that file under every route exposes all 46 H1s to crawlers.
The existing build removes other views and publishes one document per page.
The current live crawl and corrected build each have exactly one H1 per page.
No heading text, CSS or heading hierarchy needed changing. The generator and
regression tests now fail if a published page has more or fewer than one H1.
Bing's older 46-page warning is not reproducible on current production; obtain
the scan timestamp/export and run a fresh scan after release.

4. Sitemap and Google Search Console "Couldn't fetch"
Current public evidence: /sitemap.xml returns HTTPS 200, application/xml, no
redirect on the canonical host, and exactly 46 distinct canonical URLs under
http://www.sitemaps.org/schemas/sitemap/0.9. Every listed URL returned HTTP 200
without a redirect and has a matching self-canonical. No listed page has a
noindex meta or X-Robots-Tag response. Local XML parsing also succeeded.
robots.txt returns 200 text/plain, allows public crawling and references the
correct absolute sitemap URL; /api/ remains disallowed.

The historical audit observed homepage HTML returned for both sitemap.xml and
robots.txt. That earlier catch-all behavior can explain failed sitemap parsing,
but it is no longer reproduced by this audit. Ordinary, Googlebot and bingbot
user-agent requests now fetch the real sitemap and robots file successfully.
These are simulated user agents, not requests from verified crawler IPs.
Consequently no current DNS, TLS, XML, redirect or content-type failure was
established for the canonical sitemap. Do not label the private GSC error fixed
solely on these checks. Required evidence: exact submitted sitemap/property,
last-read timestamp, detailed GSC error/live fetch result and host/CDN/firewall
logs at that time. Investigate transient downtime, crawler-specific blocking,
incorrect property/URL or a stale failure using that evidence. The count of
Google verification TXT records alone does not prove authenticated ownership.
The valid sitemap and robots output were retained rather than replaced.

5. Canonicals, redirects and links
All 46 live pages already have unique titles, one self-referencing canonical,
one description, viewport metadata and indexable HTML content. Kept the known
www HTTPS origin and the actual URL set. Build generation now removes an
existing canonical before adding one, preventing future duplicates. Configured
verification tags also replace a matching tag rather than duplicate it; the
requested Bing verification tag remains present once on each generated page.

Live /trade/ returned a duplicate 200 response. Added trailingSlash:false in
vercel.json to normalize slash variants to the existing slashless canonicals.
This hosting change requires post-release verification on Vercel. Existing
.html and collection-alias redirects were retained. The live HTTP apex homepage
uses two redirects (HTTP apex -> HTTPS apex -> HTTPS www). HTTPS apex and HTTP
www reach the preferred homepage in one hop. The sitemap already uses the
direct final URLs. A single-hop HTTP apex redirect is an optional hosting-level
improvement; it was not changed in DNS or claimed as implemented here.

Four Custom-page pathway links used #enquire despite base href="/", causing
native navigation to resolve to the homepage fragment. Updated their source
targets to custom.html#enquire, compiled as /custom#enquire. Existing preset
behavior and design were preserved. The new audit resolves links against the
actual document base, checks target IDs, and reports placeholder links.

6. Structured data and performance
Retained existing Organization, WebSite, page, BreadcrumbList and Product data.
JSON-LD parses and the product names/contact details match authored content.
No prices, offers, reviews or ratings were invented. Product rich-result
eligibility is not claimed; Google's product enhancements may require offer,
review or aggregate-rating information that the visible site does not supply.

Retained existing responsive WebP generation, dimensions, native image lazy
loading and early loading of important imagery. Homepage HTML is about 43 KB
instead of the roughly 566 KB all-view source; largest generated page is below
100 KB. Existing optimized hero files remain below 300 KB each. These are file
measurements, not measured Core Web Vitals or a Lighthouse performance score.
Styles, responsive rules, animations, branding and page content were preserved.

ALTERNATIVE HOSTING IF VERCEL REMAINS BLOCKED
Use a Node-capable host with HTTPS and the existing custom domain, or a static
host with a separately hosted enquiry endpoint. With Node: extract the full
project, configure mail environment settings in the provider's secret store,
run npm ci and npm run build, and start with npm start behind the host's HTTPS
reverse proxy. Preserve the preferred www host and permanent redirects.
With static hosting: publish the CONTENTS of dist/; configure extensionless
HTML URLs, real 404s, slash normalization and alias redirects from
dist/site-manifest.json. Serve robots.txt as text/plain and sitemap.xml as XML.
Do not use a universal SPA fallback. A static-only upload will not provide
/api/enquiry: configure and test that backend before switching the live site.
Plan any domain cutover and rollback with the owner. No migration was performed.
